# Checkpoint A2 — Browser Sessions and Replay Resistance

Date: 2026-09-02

## Accepted scope

- `POST /api/v1/auth/login` authenticates PostgreSQL-backed users without revealing whether an
  email is unknown, disabled, locked or has a wrong password.
- Five failed logins lock an account for 15 minutes, including five concurrent failures.
- Login issues a 15-minute access JWT and a seven-day opaque refresh token. Only the HMAC-SHA-256
  refresh-token hash is stored in PostgreSQL.
- `GET /api/v1/auth/me` and every protected administrator route reload the session, current account
  status, role and Super Admin authority from PostgreSQL instead of trusting role claims in a JWT.
- Pending users can inspect their identity and change the one-time password, but cannot use normal
  protected routes. A successful change activates the account and revokes its other sessions.
- `POST /api/v1/auth/refresh` requires the exact configured frontend Origin and rotates the refresh
  token with a conditional single-use database update.
- Concurrent use of one refresh token produces one `200` and one `401`. Reuse of a replaced token
  revokes the active session family and appends `SESSION_REUSE_DETECTED` audit evidence.
- `POST /api/v1/auth/logout` is idempotent, clears the cookie with matching attributes and revokes
  only the selected session. Account and password changes use the same internal bulk-revocation
  service inside their existing transactions.
- Authentication endpoints are rate-limited. Browser cookies are `HttpOnly`, `SameSite=Strict`,
  scoped to `/api/v1/auth`, and add `Secure` in production. Auth responses are `no-store`.

## Contract boundary

Checkpoint A2 exposes login, current-user, password-change, refresh and logout contracts. Farm,
plot and station authorization remains deliberately out of scope until IA-6. Client Developer API
keys remain out of scope until IA-7.

## Evidence

- TDD observed the session suite fail with missing `404` routes before implementation and pass after
  conditional rotation, replay revocation, Origin validation and logout were added.
- A separate regression test observed concurrent login failures bypassing `lockedUntil`, then passed
  after the failed-login counter used the atomic PostgreSQL update result.
- `17` test files and `92` tests passed, including `13` authentication integration tests.
- Formatting, lint, TypeScript typecheck, production build, dependency audit and Git whitespace
  checks passed.
- Dependency audit found no known vulnerabilities and no unapproved dependency build scripts.
- Docker reported PostgreSQL `17.6` healthy on `127.0.0.1:5432`; the `iot_dev` migration status is up
  to date and its persistent storage remains under `E:\IoT-data\postgres`.
